# Requisitos do Sistema - VulcanTech Smart Metals S.A.
**Norma de Referência:** ISO/IEC/IEEE 29148  
**Projeto:** Monitoramento Preditivo, OEE e Visão Computacional para Parque Fabril Inteligente  
**Status:** Aprovado  
**Versão:** 1.0.0  

---

## 1. Requisitos Funcionais (RF)

| ID | Descrição | Tipo / Origem | Critério de Aceitação |
|---|---|---|---|
| **RF-001** | **Quantificação de Ausência de Dados (NaNs)**: O sistema deve mensurar e reportar a taxa percentual de valores ausentes por célula (`id_celula`) e por liga metálica (`liga_metalica`). | Explícito (Etapa 1.1) | Relatório ou dicionário com contagem/percentual exato de NaNs para cada feature por grupo. |
| **RF-002** | **Interpolação Temporal Condicional**: O sistema deve preencher lacunas de leituras temporais de sensores agrupando por equipamento (`id_celula`) ordenado cronologicamente. | Explícito (Etapa 1.1) | Nenhuma descontinuidade temporal artificial entre células diferentes; dados interpolados respeitando o histórico contínuo da mesma célula. |
| **RF-003** | **Saneamento de Ruído Físico e Sensores Defeituosos**: O sistema deve identificar e filtrar leituras impossíveis/anômalas de sensores (vibração RMS negativa `-99.0 mm/s`, temperaturas aberrantes `999.9 °C`, pressões negativas `-1.0 bar`) usando limites físicos e Z-Score condicional à liga metálica. | Explícito (Etapa 1.2) | Valores fora das faixas físicas operacionais ou com Z-score extremo condicionado à liga substituídos ou limpos. |
| **RF-004** | **Cálculo de Janelas Móveis (Rolling Features)**: O sistema deve calcular médias móveis (*Rolling Mean*) e desvios padrão (*Rolling Std*) em janelas de 30 minutos (6 amostras de 5 min) e 2 horas (24 amostras de 5 min). | Explícito (Etapa 1.3) | Colunas de médias e desvios móveis geradas para as variáveis de processo sem vazamento temporal (*look-ahead bias*). |
| **RF-005** | **Cálculo do Índice de Esforço Mecânico (IEM)**: O sistema deve computar o índice derivado: `IEM = (Torque * Vibracao_RMS) / (Vazao_Refrigerante + 1)`. | Explícito (Etapa 1.3) | Nova coluna `indice_esforco_mecanico` calculada numericamente estável para cada amostra. |
| **RF-006** | **Normalização por Lote / Liga Metálica**: O sistema deve normalizar variáveis de processo dividindo-as pela média histórica da respectiva `liga_metalica`, mitigando falsos alarmes causados por materiais de alta dureza (ex: Titânio Ti6Al4V vs Alumínio 7075). | Explícito (Etapa 1.3) | Sensores normalizados em relação à baseline de cada material; redução comprovada de desvio padrão entre ligas normais. |
| **RF-007** | **Divisão Temporal de Dados**: O particionamento em conjunto de treino e teste deve seguir rigorosamente a ordem temporal na proporção 70% treino e 30% teste. | Explícito (Etapa 2.1) | Particionamento temporal estrito, vedado sorteio aleatório (*shuffling*), evitando contaminação de dados futuros. |
| **RF-008** | **Balanceamento de Classes para Treinamento**: O pipeline de aprendizado deve tratar a raridade das falhas por ponderação de classes (`class_weight='balanced'`) ou balanceamento sintético. | Explícito (Etapa 2.1) | Treinamento dos modelos com pesos ajustados para classes minoritárias (falhas 1, 2 e 3). |
| **RF-009** | **Modelagem Supervisionada Multiclasse**: O sistema deve prover e comparar algoritmos ensemble para classificar os 4 alvos operacionais: `0 = Normal`, `1 = Desgaste de Ferramenta`, `2 = Falha de Refrigeração`, `3 = Desalinhamento / Trinca`. | Explícito (Etapa 2.2) | Modelos treinados capazes de inferir as 4 classes com probabilidades e métricas comparativas. |
| **RF-010** | **Cálculo Preditivo de Impacto no OEE**: O sistema deve estimar o impacto do estado operacional predito no indicador global de OEE (*Overall Equipment Effectiveness*), penalizando Disponibilidade (risco de parada iminente) ou Qualidade (desvio de processo/pressão/vazão). | Explícito (Etapa 2.3) | Função que calcula Disponibilidade, Performance, Qualidade e OEE final ajustados pelo diagnóstico predito. |
| **RF-011** | **Explicabilidade e Métricas de MLOps**: O sistema deve calcular Matriz de Confusão, Recall por classe de falha (priorizando Recall >= 90% nas falhas críticas), importância de atributos (*Feature Importances* ou SHAP) e exportar o pipeline treinado via `joblib`. | Explícito (Etapa 2.4 e Critérios) | Relatório de avaliação contendo Recall por classe, matriz de confusão e arquivos `.joblib` persistidos. |
| **RF-012** | **Inspeção Óptica de Cordão de Solda (Visão Computacional)**: O subsistema óptico deve aplicar filtro de nitidez, conversão para escala de cinza, detecção de bordas Canny e análise de contornos para quantificar porosidade e descontinuidade geométrica. | Explícito (Etapa 3.1) | Algoritmo que retorna taxa de porosidade (área de poros / área total) e status de continuidade do cordão. |
| **RF-013** | **Análise Termográfica da Zona Afetada pelo Calor (HAZ)**: O subsistema termográfico deve converter imagens para o espaço de cores HSV e aplicar limiarização (*thresholding*) para isolar e quantificar áreas com sobreaquecimento crítico. | Explícito (Etapa 3.1) | Identificação de pontos quentes com máscara binária HSV e percentual de área superaquecida. |
| **RF-014** | **API RESTful de Inferência em Tempo Real**: Endpoint `POST /predict` que recebe telemetria de uma leitura em tempo real e retorna: diagnóstico de falha (código e nome), probabilidade de confiança e ação industrial recomendada (`MANTER_OPERACAO`, `REDUZIR_VELOCIDADE_50%`, `INTERROMPER_EMERGENCIA`). | Explícito (Etapa 3.2) | Resposta HTTP 200 com payload JSON validado via Pydantic contendo classe, confiança e ação industrial prescritiva. |
| **RF-015** | **API RESTful de Inferência em Lote**: Endpoint `POST /predict-batch` que recebe uma lista de telemetrias e retorna os diagnósticos e ações industriais para múltiplos sensores/máquinas. | Explícito (Etapa 3.2) | Resposta HTTP 200 com array de predições otimizadas em batch. |
| **RF-016** | **API Endpoint de Checagem de Saúde**: Endpoint `GET /health` que reporta status do serviço, uptime, versão e métricas de sistema (uso de memória e CPU). | Explícito (Etapa 3.2) | Resposta HTTP 200 com status "healthy", versão da aplicação e métricas de recursos. |
| **RF-017** | **Conteinerização Edge**: O sistema deve dispor de `Dockerfile` enxuto e `docker-compose.yml` prontos para execução em nós de computação de borda (*Edge Computing*) no chão de fábrica. | Explícito (Etapa 3.3) | Contêiner funcional, sem dependências desnecessárias, expondo a API RESTful e documentação interativa. |
| **RF-018** | **Parecer Técnico Regulatório e Sustentabilidade**: Documentação formal integrando LGPD no chão de fábrica, enquadramento sob o regulamento EU AI Act e análise de eficiência energética/redução de refugo metálico (ESG). | Explícito (Etapa 3.4 e Critérios) | Relatório técnico detalhado com fundamentação jurídica, técnica e de sustentabilidade industrial. |

## 2. Requisitos Não Funcionais (RNF)

| ID | Descrição | Categoria | Tipo / Origem | Critério de Aceitação |
|---|---|---|---|---|
| **RNF-001** | **Consumo Mínimo de Recursos (RAM/CPU)**: A aplicação em tempo de execução deve operar com menos de 150 MB de memória RAM e uso mínimo de CPU em nós Edge. | Eficiência / Recursos | Explícito (Instruções) / Inferido | Processo Python do servidor ocupando < 150 MB em repouso e inferência sub-10ms. |
| **RNF-002** | **Arquitetura Desacoplada (Clean Architecture / Hexagonal)**: O núcleo de negócio (`src/core/`) não deve possuir acoplamento com bibliotecas de I/O, rede ou frameworks web (`src/adapters/`). | Manutenibilidade / Arquitetura | Explícito (Instruções) | Nenhum `import` de `fastapi`, `uvicorn`, ou adaptadores dentro de `src/core/`. |
| **RNF-003** | **Validação e Tipagem Estrita de Dados**: Todos os esquemas de entrada e saída da API RESTful devem ser validados via Pydantic v2. | Confiabilidade / Integridade | Explícito (Etapa 3.2) | Erros 422 descritivos retornados para payloads com campos inválidos ou fora dos limites físicos. |
| **RNF-004** | **Tratamento Seguro de Erros e Logging Estruturado**: Mensagens de erro claras e logs mínimos e informativos sem vazamento de dados confidenciais ou segredos industriais. | Segurança / Operabilidade | Explícito (Instruções) | Logging via biblioteca padrão `logging` em formato JSON/legível, sem credenciais. |
| **RNF-005** | **Zero Dependências Supérfluas**: Uso prioritário da biblioteca padrão Python e pacotes estritamente necessários para Ciência de Dados e Edge API (`pandas`, `numpy`, `scipy`, `scikit-learn`, `opencv-python`, `fastapi`, `pydantic`, `uvicorn`, `joblib`). | Eficiência | Explícito (Instruções) | Sem ORM, sem bancos pesados, sem Docker desktop obrigatório para testes locais. |
| **RNF-006** | **Compatibilidade Multiplataforma**: O código e os testes devem executar nativamente em Linux, macOS e Windows sem dependência de comandos bash específicos. | Portabilidade | Explícito (Instruções) | Testes e scripts executáveis via `python -m pytest` e scripts universais. |
| **RNF-007** | **Cobertura de Testes Automatizados**: Todos os requisitos funcionais devem possuir testes unitários e de integração automatizados verificáveis. | Qualidade / Rastreabilidade | Explícito (Instruções) | 100% dos módulos de `core` e endpoints da API cobertos com asserções válidas. |
